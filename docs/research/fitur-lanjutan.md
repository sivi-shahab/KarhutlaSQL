# Research report: KarhutlaSQL must become a policy engine, not just a gateway

KarhutlaSQL's current feature list (auth, OIDC, per-catalog permissions, session kill, metrics, queuing, JSON audit, TLS/mTLS, timeouts, CLI) is already **on par with GizmoSQL Core plus part of Enterprise**, but it has not yet touched the layer bank auditors look for most: row/column-level access control tied to data classification, a per-column trail of PII access that can answer data-subject requests within 3x24 hours, and proof of integrity for OJK reporting figures. This research finds that Indonesian regulation never mentions "row-level security" or "masking", but it does require classification of personal data (POJK 11/2022 Article 45), a security level matched to sensitivity (PDP Law Article 35), an audit trail of all IT activity (POJK 11/2022 Article 54), and processing records plus proof of compliance (PP 33/2026 Articles 74 and 138), with sanctions of up to 2% of annual revenue taking full effect on **16 January 2027** ([Rajah & Tann](https://www.rajahtannasia.com/viewpoints/pdp-law-updates-the-pdp-implementing-regulation-is-out-and-it-clarifies-some-key-questions-under-indonesias-pdp-law/)). Because DuckDB has no notion of users, GRANT, HMAC, or a result cache, all of these controls have to be built in the Go server layer, and this is exactly where KarhutlaSQL can differentiate itself from GizmoSQL, whose README mentions neither RLS, masking, nor an audit log ([GitHub gizmosql](https://github.com/gizmodata/gizmosql)). Core recommendations for v1.x: tag-based masking and row filters rewritten by the server, per-column access-history audit written to WORM Parquet with 10-year retention, Trino-style resource groups on top of `golang.org/x/sync/semaphore`, a `query_history` table based on `duckdb_get_profiling_info`, and a Go MCP server in the same binary. For v2: DuckLake as the multi-writer path and version-locked reporting snapshots, a Delta Sharing endpoint, and a Postgres-wire listener for Power BI/Excel. An important timing note: **DuckDB 2.0.0 and DuckLake 1.1 were released today, 21 October 2026**, and both materially change the HA architecture options ([DuckDB blog 2.0](https://duckdb.org/2026/08/17/duckdb-20-highlights.html)).

## DuckDB 2.0 and DuckLake 1.1 change the HA map, not the governance map

Release 2.0 ("Cinnamon Teal") brings four things directly relevant to a server: **aggregations now spill to disk** when they exceed memory, async I/O throughout the engine, a "metrics layer rework for long-running instances", and a **C API with a stable ABI** so extensions no longer need rebuilding every release ([DuckDB blog 2.0](https://duckdb.org/2026/08/17/duckdb-20-highlights.html)). The first reduces the OOM risk of bank analytical queries (aggregations per branch/segment with high cardinality) that were previously cancelled outright ([DuckDB memory management](https://duckdb.org/2024/07/09/memory-management.html)); the last makes it easier for KarhutlaSQL to ship custom extensions (e.g. an HMAC UDF) via `CREATE EXTENSION REPOSITORY` with a signing key as an offline mirror in air-gapped environments. Quack, DuckDB's official HTTP client-server protocol, is now declared mature in 2.0 after a beta in 1.5.3, but it uses `application/duckdb` serialization, not Arrow Flight ([DuckDB Quack](https://duckdb.org/docs/2.0/quack/overview.html)); Quack is not a KarhutlaSQL competitor but a 2027 backend option for a single "primary" DuckDB process accepting writes from many Flight SQL pods.

The bigger change comes from DuckLake 1.1, declared **production-ready with a PostgreSQL catalog** as the recommended multi-writer/multi-reader path, replacing the "one RW process, N READ_ONLY processes, copy snapshot files" choreography ([DuckDB concurrency 2.0](https://duckdb.org/docs/2.0/connect/concurrency.html)). With DuckLake, every KarhutlaSQL pod can `ATTACH 'ducklake:postgres:...' (DATA_PATH 's3://bucket/')` to MinIO and write with automatically retried optimistic concurrency; MotherDuck claims ~100 transactions per second versus ~1 for older lakehouse formats, plus data inlining for small inserts and a single `CHECKPOINT` for flush/compact/vacuum ([MotherDuck DuckLake deep dive](https://motherduck.com/blog/ducklake-architecture-deep-dive/)). Time travel `AT (VERSION => n)`, `ATTACH (SNAPSHOT_VERSION n)`, and per-file Parquet encryption with keys in the catalog ([DuckLake encryption](https://ducklake.select/docs/stable/duckdb/advanced_features/encryption)) are free raw material for the OJK reporting features discussed below. The practical implication: do not invest v1.x effort in a file-copy read-replica mechanism; build a neutral "catalog registry" abstraction, then make DuckLake+Postgres+MinIO the v2 reference topology. What does **not** change in 2.0: DuckDB still has no user/role, no `current_user`, no HMAC, no built-in query timeout, no result cache, and no materialized views ([DuckDB utility functions](https://duckdb.org/docs/2.0/sql/functions/utility.html); [Securing DuckDB](https://duckdb.org/docs/2.0/operations_manual/securing_duckdb/overview.html)). All governance remains the Go server's job.

## Row- and column-level access control is the largest gap against the PDP Law

Almost every customer transaction and balance column counts as **specific personal data** because PDP Law Article 4 includes "personal financial data" alongside biometrics and health ([Mondaq](https://www.mondaq.com/data-protection/1242654/law-no-27-of-2022-on-personal-data-protection-a-high-level-overview-on-the-new-personal-data-protection-law)). Article 35 requires a security level matched to sensitivity, POJK 11/2022 Article 45(1)(a) requires banks to classify personal data, and SEOJK 29/2022 Appendix I.b demands least privilege, a single unique ID, and the four-eyes principle ([POJK 11/2022](https://peraturan.go.id/files/pojk11-2022.pdf); [SEOJK 29/2022](https://www.ojk.go.id/id/regulasi/Documents/Pages/Ketahanan-dan-Keamanan-Siber-Bagi-Bank-Umum/SEOJK%2029%20SEOJK.03%202022.pdf)). The planned per-catalog permission only answers "may this user open the database or not"; an auditor will ask why a churn analyst can see raw NIK (national ID) and account numbers.

Industry patterns have converged and can be copied directly. Trino applies row filters as boolean expressions and column masks as SQL expressions in first-match-wins JSON rules with default deny and hot reload via `security.refresh-period` ([Trino file-based access control](https://trino.io/docs/current/security/file-system-access-control.html)); Trino-OPA defines a JSON contract returning `allow`, `{"expression"}` for row filters, and `{"viewExpression","index"}` for masks ([Trino OPA](https://trino.io/docs/current/security/opa-access-control.html)). Snowflake and Databricks bind policies to **tags**, not columns, so new tables in a tagged schema are protected automatically ([Snowflake tag-based policies](https://docs.snowflake.com/en/user-guide/tag-based-policies); [Databricks ABAC](https://docs.databricks.com/aws/data-governance/unity-catalog/abac)). Dremio uses boolean UDFs and same-typed masking UDFs that may read a user→region lookup table ([Dremio row/column policies](https://docs.dremio.com/25.x/security/rbac/row-column-policies-udf)). An implementation in Go+DuckDB follows this recipe: session identity (user, groups, business unit, `unmask:<tag>` attributes) injected from the JWT into the DuckDB connection as session variables before `lock_configuration=true`; a governance catalog in a `policy.duckdb` file encrypted with `ENCRYPTION_KEY`, `ATTACH (READ_ONLY)` to every session, holding the tables `datasets`, `columns`, `tags`, `column_tags`, `policies`, `policy_approvals`; masking as persistent `CREATE MACRO mask_nik(v)`, `mask_rekening(v)`, `bucket_saldo(v)` in that file ([DuckDB CREATE MACRO](https://duckdb.org/docs/2.0/sql/statements/create_macro.html)); and a SQL rewriter in the server that replaces tagged columns with `macro(col)` and adds the `WHERE` from the policy engine before execution. Without a parser, the cheap fallback is per-persona views generated from the catalog. For policy-as-code, store rules as Trino-style JSON or Rego in Git and include the policy version hash in every audit record. Stable pseudonymization needs a keyed hash that DuckDB does not have; `hash()` is forbidden because its values may change between versions ([DuckDB utility functions](https://duckdb.org/docs/2.0/sql/functions/utility.html)), so use `sha256(salt || value)` with a salt from Vault/HSM, or an HMAC UDF via a 2.0 stable-ABI extension.

## Per-column access history and proof of integrity for OJK reports

The planned per-statement JSON audit log is not enough for two questions that will certainly be asked: "who accessed customer X's data in this period" and "which version of the data was this report figure computed from". POJK 11/2022 Article 54(2) requires an audit trail of all IT activity, PP 33/2026 Article 74 requires a record of all processing activities (ROPA) including retention periods, data-subject requests must be answered within **3x24 hours** after verification, and 3x24-hour breach notification must be backed by "logs and forensic reports" ([Rajah & Tann](https://www.rajahtannasia.com/viewpoints/pdp-law-updates-the-pdp-implementing-regulation-is-out-and-it-clarifies-some-key-questions-under-indonesias-pdp-law/); [RSM Indonesia](https://www.rsm.global/indonesia/en/node/439)). There is no explicit log retention figure in POJK or PP 33; the conservative **10 years** comes from Law 8/1997 Article 11 for financial documents ([Hukumonline](https://www.hukumonline.com/klinik/a/jangka-waktu-penyimpanan-dokumen-perusahaan-lt646efc4036ca5)). The right model is Snowflake ACCESS_HISTORY: one row per statement with `direct_objects_accessed`, `base_objects_accessed` (base tables behind views, including filter/join columns), and `policies_referenced` ([Snowflake access history](https://docs.snowflake.com/en/user-guide/access-history)). DuckDB's built-in `QueryLog` is insufficient because it is unstructured and has no user ([DuckDB logging](https://duckdb.org/docs/2.0/operations_manual/logging/overview.html)); the server must record the parser's resolution itself (columns touched down to the base table), the PII tags hit, and the masks applied, then write them as daily-partitioned Parquet to a MinIO bucket with object-lock. From that table, the endpoint `audit.pii_access(subject_id, from, to)` answers DSARs within the SLA.

For OJK reporting, the new POJK 22/2025 regime (effective 2 October 2025) digitizes all reporting through the OJK reporting system with master reports and a responsible reporting officer ([OJK POJK 22/2025](https://ojk.go.id/id/regulasi/Pages/POJK-22-Tahun-2025-Pelaporan-Bank-Umum-Melalui-Sistem-Pelaporan-Otoritas-Jasa-Keuangan.aspx)), while SLIK (the credit information system) requires debtor reports that are "complete, accurate, current, whole, and timely" no later than the 12th of the month, with a correction fine of Rp50,000 per debtor per day and mandatory segregation of duties between preparer, verifier, and submitter ([POJK 18/2017](https://peraturan.go.id/files/ojk18-2017bt.pdf)). Server features with immediate value: **snapshot-bound report runs** (a `report_runs(report, period, snapshot_version, sql_hash, checksum, created_by, verified_by)` table that always queries `AT (VERSION => n)` in DuckLake), snapshot retention of at least 6 months aligned with the APOLO correction window ([Summary of POJK 12/2019](https://ojk.go.id/id/regulasi/Documents/Pages/Pelaporan-Bank-Umum-Melalui-Sistem-Pelaporan-Otoritas-Jasa-Keuangan/Ringkasan%20POJK%2012-2019.pdf)), **signed export** with a SHA-256 manifest + Ed25519 by the server, and a data-quality gate of SQL assertions that blocks the "verified" status. This is not a workflow engine, just a system table plus three statuses with different roles.

Data residency and cryptography round out this cluster. POJK 11/2022 Article 35(1) requires electronic systems in data centers and DRCs located in Indonesia; the OJK FAQ confirms core banking may not be offshore ([OJK FAQ](https://ojk.go.id:443/id/regulasi/Documents/Pages/Penyelenggaraan-Teknologi-Informasi-Oleh-Bank-Umum/FAQ%20POJK%2011%20-%2003%20-%202022.pdf)). The technical guardrail is cheap: a per-session prologue `SET enable_external_access=false; SET disabled_filesystems='LocalFileSystem'; SET allowed_directories=[...]; SET lock_configuration=true`, only registered catalogs can be ATTACHed, and S3 secrets are created as **temporary** with `SCOPE 's3://bucket/'` to the internal MinIO endpoint, because `CREATE PERSISTENT SECRET` writes credentials **unencrypted** to disk ([DuckDB secrets manager](https://duckdb.org/docs/2.0/configuration/secrets_manager.html)). DuckDB at-rest encryption (AES-256-GCM since 1.4) is suitable for policy/audit/cache files, but DuckDB itself states it does not yet meet NIST requirements and does not cover key rotation ([DuckDB encryption blog](https://duckdb.org/2025/11/19/encryption-in-duckdb)); make LUKS/MinIO KES/HSM the primary layer and fetch the `ENCRYPTION_KEY` from Vault at startup.

## Workload management and observability decide whether the server survives in production

The DuckDB knobs that actually exist are per instance: `memory_limit`, `threads`, `max_temp_directory_size`, `temp_directory`, and `lock_configuration` + `allowed_configs` ([DuckDB configuration](https://duckdb.org/docs/2.0/configuration/overview.html)), plus per-connection `duckdb_interrupt` and `duckdb_query_progress` ([DuckDB C API](https://duckdb.org/docs/2.0/clients/c/connect.html)). There are no resource groups, priorities, or per-user quotas. The planned statement queuing should be designed directly as **Trino-style resource groups**: `hardConcurrencyLimit`, `maxQueued` (exceeding it → reject), `softMemoryLimit`, `fair`/`weighted` scheduling, and first-match selectors on `user`, `userGroup`, `source`, `queryType`, `clientTags` ([Trino resource groups](https://trino.io/docs/current/admin/resource-groups.html)). Dremio adds two separate timeouts, an enqueued time limit defaulting to 5 minutes and a runtime limit, plus a reject action in routing rules ([Dremio WLM](https://docs.dremio.com/current/admin/workloads/workload-management)); ClickHouse adds per-interval quotas (queries, read_rows, execution_time per hour) that reset on restart ([ClickHouse quotas](https://clickhouse.com/docs/operations/quotas)). In Go: a weighted semaphore per group with a bounded queue, rejection with a retriable gRPC `RESOURCE_EXHAUSTED` (GizmoSQL uses `UNAVAILABLE` when `--max-sessions` is reached, with admin bypass ([GizmoSQL docs](https://docs.gizmosql.com))), queued and execution timeouts calling `duckdb_interrupt`, and a client timeout that cancels the query when the DoGet stream is abandoned. Hard memory isolation is only possible with separate DuckDB instances per load class, exactly the Watershed pattern that runs 30 GB and 180 GB variants behind a router and reaches >95% success rate ([Watershed](https://watershed.com/blog/how-watershed-uses-duckdb-to-reliably-compute-customer-footprints)). Cost estimation is not worth pursuing: Dremio itself admits `query_cost()` is not a reliable predictor; use duration history per normalized query hash.

The result cache is the feature with the highest benefit/effort ratio for BI dashboards: results are already Arrow IPC (the Flight wire format, no re-encoding), key = hash(normalized SQL + parameters + identity + session options), default TTL 60 seconds, admission by `min_query_duration`/`min_query_runs`, a 20 MB per-entry limit, not shared between users unless privileges are identical, and skipped for non-deterministic functions, following the semantics of ClickHouse ([ClickHouse query cache](https://clickhouse.com/docs/operations/query-cache)) and Dremio ([Dremio reflections](https://docs.dremio.com/current/sonar/reflections/)). With DuckLake, the catalog snapshot ID goes into the cache key so invalidation is equivalent to Snowflake's "data did not change". Materialized views can simply be tables refreshed on a schedule by an internal scheduler; IVM for DuckDB is only a research prototype without join support ([cwida/ivm-extension](https://github.com/cwida/ivm-extension)).

Observability beyond Prometheus is built from per-connection `duckdb_get_profiling_info` after each query with limited `tracked_metrics`, not global `enable_logging`, which risks capturing secrets ([DuckDB profiling](https://duckdb.org/docs/2.0/dev/profiling.html)). A `query_history` table (query_id, session, user, resource_group, sql_hash, redacted sql_text, state, queued_ms, exec_ms, rows_returned, bytes_sent, peak_memory, rows_scanned, cache_usage, error) also becomes the source for the slow-query log (store `EXPLAIN ANALYZE (FORMAT json)` only for slow queries), daily chargeback per team from JWT claims, and quota input. OTel via the `otelgrpc` interceptor gives a span per Flight RPC with the attributes `enduser.id`, `flightsql.resource_group`, `flightsql.queued_ms`, sent to an on-prem Collector + Tempo; the ADBC Go driver already supports client-side tracing ([ADBC Flight SQL driver](https://arrow.apache.org/adbc/current/driver/flight_sql.html)). On the operations side, tiered backup uses `COPY FROM DATABASE` (hot) and `EXPORT DATABASE (FORMAT parquet)` (cold, portable across storage versions) ([DuckDB EXPORT](https://duckdb.org/docs/2.0/sql/statements/export.html)), and for DuckLake it is enough to back up the Postgres catalog plus MinIO bucket versioning. An admin API as custom Flight `DoAction`s (list/kill session, cancel query, reload config, clear cache, attach/detach catalog, snapshot_now, health) and a readiness probe based on a GizmoSQL-style health-check query complete the Kubernetes deployment: a writer StatefulSet + reader Deployment, `preStop` = gRPC drain + `CHECKPOINT`.

## AI integration and the client ecosystem decide adoption inside the bank

An MCP server is the cheapest and most valuable AI-era feature because KarhutlaSQL already has auth, policy, and timeouts; MCP is just UX. GizmoSQL-MCP (TypeScript) exposes `list_catalogs/schemas/tables`, `describe_table`, `run_query` with a hard cap of 500 rows and a 60-second timeout, `explain_query`, an opt-in `execute_statement` marked destructive, and DDL resources; stdio + Streamable HTTP transports as an OAuth 2.1 resource server ([GizmoSQL-MCP](https://github.com/gizmodata/gizmosql-mcp); [MCP changelog 2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18/changelog)). KarhutlaSQL should write it **in Go in the same binary** with an identical tool set, validating internal Keycloak JWTs via the already planned JWKS. Text-to-SQL guardrails must be enforced in the server, not in the prompt: a real SQL parser that only accepts one SELECT, LIMIT injection, tenant scoping from the authenticated session, and audit per tool call ([Draxlr](https://www.draxlr.com/blogs/mcp-server-read-only-tenant-aware-sql-access/)). An `ai_sandbox` connection profile (read_only + `enable_external_access=false` + `allowed_directories` + `lock_configuration` + a small `memory_limit`) is DuckDB's official recommendation for untrusted SQL ([Securing DuckDB](https://duckdb.org/docs/2.0/operations_manual/securing_duckdb/overview.html)). The replacement for Cortex Analyst/Genie in an air-gapped environment is a system table `verified_queries(name, question, sql, verified_by, verified_at)` plus a YAML semantic model (tables, relationships, metrics, dimensions) exposed as an MCP resource ([Snowflake VQR](https://docs.snowflake.com/LIMITEDACCESS/snowflake-cortex/cortex-analyst-vqr)). Vector search remains "preview": the VSS extension is explicitly not recommended for production because persistence is experimental and indexes risk corruption ([DuckDB VSS](https://duckdb.org/docs/current/core_extensions/vss)); brute-force `array_cosine_distance` is safe for 1–2 million call-center transcript vectors.

On the client side, the ADBC Flight SQL drivers (C/C++, Python, Go, R, C#, Rust) and the universal JDBC driver come for free, but with two holes: the Flight SQL JDBC driver does not support parameterized queries and `getCatalog()` is empty ([Dremio JDBC](https://docs.dremio.com/25.x/sonar/client-applications/drivers/arrow-flight-sql-jdbc-driver)), and **Power BI provides no generic ADBC connector; refresh through the on-premises gateway stays on ODBC until Spring 2027** ([Microsoft transition to ADBC](https://learn.microsoft.com/power-query/transition-to-adbc)). For a bank that depends on Power BI and Excel, the realistic paths are Dremio's Flight SQL ODBC 0.9.0 (Windows, performance not yet optimized, cancel does not reach the server ([Dremio ODBC](https://docs.dremio.com/25.x/release-notes/arrow-flight-sql-odbc/arrow-flight-sql-odbc-090))) or a secondary **Postgres wire protocol** listener in front of the same engine, the Duckgres pattern (Go, MIT) that also provides per-user file isolation and a control plane routing sessions to workers over Flight SQL on a Unix socket ([PostHog/duckgres](https://github.com/PostHog/duckgres)). Metabase has no Flight SQL path at all ([Metabase DuckDB driver](https://github.com/motherduckdb/metabase_duckdb_driver)), so Postgres-wire is the only door. Grafana already has Flight SQL plugins from GizmoSQL and InfluxData with alerting ([Grafana GizmoSQL plugin](https://grafana.com/grafana/plugins/gizmodata-gizmosql-datasource/)); if wire-compatible, alerts on query results come for free. Superset needs a `karhutlasql://` SQLAlchemy dialect on top of `adbc_driver_flightsql`. dbt v2 bundles embedded DuckDB via ADBC and supports DuckLake in `catalogs.yml`, but has no host/port notion for a remote DuckDB ([DuckDB blog dbt Fusion](https://duckdb.org/2026/09/22/dbt-fusion)); the pragmatic path is dbt running against the same DuckLake Postgres catalog as KarhutlaSQL, or a thin `dbt-karhutlasql` adapter. Airflow already provides an `AdbcHook` with a Flight SQL backend ([Airflow apache-arrow provider](https://airflow.apache.org/docs/apache-airflow-providers-apache-arrow/stable/index.html)), so orchestration does not need to be built. For data sharing between units or subsidiaries, Delta Sharing is an open protocol with >15 clients including Power BI and Tableau, based on short-lived pre-signed URLs ([VLDB 2025](https://www.vldb.org/pvldb/vol18/p5197-puttaswamy.pdf)); a Go endpoint on top of DuckLake/Parquet in MinIO is a differentiating v2 feature.

## Priorities: v1.x locks in compliance, v2 locks in scale

The PP 33/2026 deadline (full sanctions on 16 January 2027) and OJK PADK 2026 (effective 1 March 2026, revoking SEOJK 21/2017, covering personal data protection and internal audit ([PADK 1/2026 abstract](https://ojk.go.id/id/regulasi/Documents/Pages/PADK-1-Tahun-2026-Penyelenggaraan-Teknologi-Informasi-oleh-Bank-Umum/Abstrak%20PADK%201%20Tahun%202026%20Penyelenggaraan%20Teknologi%20Informasi%20oleh%20Bank%20Umum.pdf))) put governance in v1.x and scale in v2.

| Priority | v1.x (Q4 2026 – Q1 2027) | v2 (2027) |
|---|---|---|
| **Must** | Session identity + attributes; default-deny object privileges; column masking + tags/classification; row filters via rewrite; per-column access history to WORM Parquet, 10-year retention, OJK export; residency/egress guardrail + SCOPE'd temporary secrets; resource groups + two timeouts + client timeout; `query_history` + slow-query log; `ai_sandbox` profile + SELECT-only parser; DoAction admin API + health check | DuckLake (Postgres + MinIO) as the reference multi-writer topology; snapshot-bound report runs + signed export + DQ gate; instance per load class/tenant; Postgres-wire listener |
| **Should** | Policy-as-code JSON/Rego in Git + hot reload + four-eyes; `audit.pii_access` endpoint; Arrow IPC result cache; OTel tracing; per-team quotas + chargeback; Go MCP server; bulk ingest + `PollFlightInfo` + full `GetSqlInfo`; tiered backup + schema migrations; Vault/HSM key management; GitOps policy CLI | Purpose tagging + ROPA registry; Delta Sharing endpoint; verified queries + semantic model; official Grafana datasource; thin dbt adapter; embedded mode |
| **Could** | Regex auto-classification; simple scheduled jobs; scheduled MVs; HTTP/WebSocket Arrow IPC endpoint; rule-based access anomaly detection | Vector search preview (brute force); Terraform provider on top of the policy CLI; Quack as the primary backend; aggregation policy (minimum group size) |

Features that should **not be built in-house**, because they already exist, are immature, or sit at the wrong layer: pipeline orchestration (Airflow `AdbcHook` and Temporal already exist; KarhutlaSQL only needs a simple SQL scheduler); a full alert engine (Grafana alerting on top of a Flight SQL datasource); an identity provider and user directory (on-prem Keycloak/AD via the already planned OIDC/JWKS, do not store passwords in the server); an in-house ODBC driver (use Dremio 0.9.0 or wait for ADBC consolidation; a Postgres-wire listener gives wider coverage for similar effort); persistent HNSW or a vector database (VSS is not production-ready, is not counted against `memory_limit`, and its index cannot be recovered after a crash); true IVM/materialized views and Dremio-Reflections-style automatic query rewrite (needs access to DuckDB's optimizer); a query cost estimator (Dremio itself says it is unreliable); at-rest encryption as the only layer (DuckDB is not yet NIST-compliant and has no key rotation; LUKS/MinIO KES/HSM remain mandatory); a native CDC connector (Debezium → Kafka/Redpanda → consumer, or DuckLake data inlining); file-copy read replicas (DuckLake 1.1 makes them obsolete); a custom Kubernetes operator before StatefulSet/Deployment + Helm have proven insufficient; and a full Cube-style semantic layer (YAML + verified queries is enough; Cube/Malloy can be layered on top if needed).

## Conclusion

The most important shift from this research is how to position KarhutlaSQL: not "GizmoSQL in Go" but a **policy enforcement point** for bank analytical data, with DuckDB as an engine that is deliberately kept ignorant of identity. Everything DuckDB lacks (users, GRANT, RLS, masking, HMAC, result cache, resource groups, access history) is exactly the space for product differentiation, and everything DuckDB 2.0/DuckLake 1.1 newly provides (aggregation spill, stable ABI, multi-writer, time travel, per-file encryption) is raw material that should be used as-is, not imitated. One design decision determines almost every Must feature: having a SQL parser and rewriter on the GetFlightInfo path. Without it, masking, row filters, per-column access history, LIMIT injection, and query-type classification all degrade to per-persona views and regexes. Invest in the parser first.

Remaining uncertainties should be verified before committing effort: Appendix I of OJK PADK 2026 (75 pages) has not been read and likely contains detailed access-control provisions replacing SEOJK 21/2017; the behaviour of `SET VARIABLE`/`getvariable()` with respect to `lock_configuration` has not been tested; `SAVEPOINT` support in DuckDB and MinIO object lock with DuckLake have not been confirmed; and the final OJK reporting file format under POJK 22/2025 has not been obtained from a primary source. All four are one-day verification tasks, and their outcome only shifts implementation details, not priorities.
